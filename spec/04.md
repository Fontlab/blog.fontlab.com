# Chapter 4 — Build Pipeline

## Entry points

There are two ways to invoke the build:

```bash
./build.sh build       # production build → docs/
./build.sh serve       # local dev server → http://localhost:8000
./build.sh clean       # wipe docs/
```

`build.sh` is intentionally thin:

```bash
#!/usr/bin/env bash
set -euo pipefail
uv run blog-fontlab "$@"
```

That's it. `uv run` activates the virtual environment, resolves the `blog-fontlab` entry point from `pyproject.toml`, and passes all arguments to the Fire CLI. No shell logic lives in `build.sh` — it all lives in Python.

## The Fire CLI

`src/blog_fontlab/cli.py` exposes a `BlogFontlab` class wired to Fire:

```python
import fire
import subprocess
from pathlib import Path

REPO_ROOT = Path(__file__).parent.parent.parent
MKDOCS_YML = REPO_ROOT / "mkdocs" / "mkdocs.yml"

class BlogFontlab:
    def build(self):
        """Build the site into docs/."""
        subprocess.run(
            ["properdocs", "build", "--config-file", str(MKDOCS_YML)],
            check=True,
        )

    def serve(self, port: int = 8000):
        """Serve locally with live reload."""
        subprocess.run(
            ["properdocs", "serve", "--config-file", str(MKDOCS_YML),
             "--dev-addr", f"127.0.0.1:{port}"],
            check=True,
        )

    def clean(self):
        """Remove the docs/ build output."""
        import shutil
        site_dir = REPO_ROOT / "docs"
        if site_dir.exists():
            shutil.rmtree(site_dir)
            print(f"Removed {site_dir}")

def main():
    fire.Fire(BlogFontlab)
```

The entry point in `pyproject.toml`:

```toml
[project.scripts]
blog-fontlab = "blog_fontlab.cli:main"
```

```toml
[tool.hatch.version]

[tool.hatch.version.raw-options]

[tool.hatch.build.hooks.vcs]
version-file = "src/blog_fontlab/__version__.py"
```

`__version__.py` is gitignored. It is generated at build time by hatch-vcs reading the most recent `v*.*.*` git tag. This means version bumps require only a tag push — no source file edits.

## uv lockfile policy

`uv.lock` is committed to the repository. The rationale:

- Reproducible builds: CI and local builds resolve to identical dependency trees
- Auditable: dependency updates are visible in pull request diffs
- Fast: `uv sync --frozen` skips resolution entirely

To update dependencies: edit `pyproject.toml` version constraints, run `uv lock`, commit both files together. Never run `uv sync` without `--frozen` in CI.

## ProperDocs invocation

The CLI delegates directly to the `properdocs` command-line tool (the ProperDocs equivalent of `mkdocs`). ProperDocs reads `mkdocs/mkdocs.yml`, which declares:

```yaml
docs_dir: ../src_docs/md
site_dir: ../docs
```

Paths are relative to `mkdocs.yml`'s location. This is standard ProperDocs/MkDocs behaviour.

## Local development cycle

1. `./build.sh serve` starts the dev server with live reload
2. Edit a file in `src_docs/md/blog/posts/`
3. Browser refreshes automatically
4. When satisfied, set `draft: false` in front-matter
5. Commit and push; tag to trigger deploy

The serve command does not write to `docs/`. It serves from an in-memory build. Only `./build.sh build` writes to disk.

## Versioning discipline

Version tags follow `v{MAJOR}.{MINOR}.{PATCH}` semver. The first public deploy is `v0.1.0`. Breaking changes to the build pipeline (e.g., major ProperDocs upgrade) warrant a minor bump. Content-only changes do not require a new tag unless a deploy is desired — a tag is a deploy trigger, not a content version.
