# Chapter 12 — Quality, Testing & Roadmap

## Local smoke tests

These run before every pull request merge, manually by the author and automatically by CI.

### Link check

Use `linkchecker` or `lychee` against the local build output:

```bash
./build.sh build
lychee --offline docs/         # internal links only, no network required
lychee docs/ --exclude-all-private  # full check including external
```

`lychee` is fast, parallel, and configurable. Add a `.lycheeignore` file to suppress known-stable external URLs that return 429 (rate limited) in CI:

```
# .lycheeignore
https://fonts.googleapis.com
https://fonts.gstatic.com
```

External link checking should run in CI on a schedule (weekly), not on every push — external URLs change independently of the repo.

### Browser render check

For significant layout changes (new CSS token, template override edit, Web Component config change):

1. `./build.sh serve`
2. Open Chrome DevTools (or use the Chrome DevTools MCP tool if running in an agent context)
3. Check the following at 1280px and 375px viewport widths:
   - `http://localhost:8000/` — home page renders without layout breaks
   - `http://localhost:8000/blog/` — paginated index shows excerpt, author, date
   - A single post URL — post content, code blocks, images render correctly
   - `http://localhost:8000/blog/archive/` — archive index loads
   - `http://localhost:8000/about/` — about page loads
4. Check the Web Component menu is visible and the local nav items appear
5. Check dark mode — page background matches the menu background (no jarring colour join)

This is a human check, not automated. Automated visual regression testing (Percy, Chromatic) is out of scope for v0.1.0.

## CI sanity checks

The `ci.yml` workflow (see [chapter 5](05.md)) runs the following assertions after every build:

```bash
# Required files exist
test -f docs/index.html
test -f docs/CNAME
test -f docs/blog/index.html
test -f docs/about/index.html

# CNAME is correct
grep -q "blog.fontlab.com" docs/CNAME

# llms.txt was generated
test -f docs/llms.txt

# No build warnings about missing authors or categories
# (properdocs exits non-zero on these — the check is implicit)
```

If any assertion fails, the build job fails and the deploy step does not run.

## Evergreen content rule

A post is evergreen if it will still be accurate and useful in two years without edits. This is an editorial standard, not a technical check. Enforced by the category allowed-list: categories like `Typography`, `OpenType`, and `Variable Fonts` naturally select for durable content. Categories like `News` or `Releases` are absent from the allowed list deliberately.

Non-evergreen content that slips through:
- Version-specific UI instructions that break when the UI changes: flag in a post comment and open an issue to update or retire
- External links to resources that have moved: fix in a focused commit with message `blog: fix dead link in "Title"`
- Factual inaccuracies discovered after publication: correct in place (this is an exception to the content-freeze rule in [chapter 10](10.md)); add an editor's note at the top of the post noting the correction and date

### Medium-term (v0.2.0)

- [ ] PR template with authoring checklist
- [ ] Scheduled weekly external link check in CI
- [ ] `llms.txt` output verified and formatted
- [ ] Custom 404 page (`docs/404.html`)
- [ ] RSS feed verified (ProperDocs blog plugin generates `/feed.xml` by default — confirm and test)

### Longer-term

**`vexy-mkdocs-tools` as single-package wrapper.** The current `pyproject.toml` lists individual plugin packages. The roadmap goal (per `IDEA.md`) is a single `vexy-mkdocs-tools` package that declares all these as its own dependencies, so the blog's `pyproject.toml` reduces to:

```toml
dependencies = [
    "vexy-mkdocs-tools>=1.0.0",  # brings properdocs, materialx, all plugins
    "fire>=0.6.0",
]
```

This would let any FontLab site use the same toolchain version without per-site dependency management. The blog is the first consumer; the pattern is proven here before being extracted.

**`llms.txt` generation quality.** The `mkdocs-llmstxt` plugin generates a basic `llms.txt`. Future work: validate the output against the [llms.txt spec](https://llmstxt.org/), add post summaries, ensure post ordering is meaningful (most recent first).

**Comment system.** Out of scope for v0.1.0. If reader feedback becomes a priority, the decision between Giscus (GitHub Discussions-backed), Disqus, and no comments at all should be made as a separate RFC. The current spec explicitly excludes it.

## Open questions

These require a decision before the corresponding feature ships. They are not blockers for v0.1.0 unless noted.

| Question | Context | Default if not decided |
|----------|---------|----------------------|
| Home page: redirect vs landing? | See [chapter 6](06.md) Option A vs B | Landing page (Option B) |
| Colour tokens: exact values? | `--fl-bg`, `--fl-accent` etc. need brand guide sign-off | Use FontLab dark blue palette as placeholder |
| RSS feed URL: `/feed.xml` or `/blog/feed.xml`? | ProperDocs default is `/blog/feed.xml`; some feed readers expect `/feed.xml` | Accept plugin default `/blog/feed.xml` |
| Comment system: add or omit? | [medium-term roadmap item] | Omit for v0.1.0 |
| Analytics: add or omit? | Privacy implications; no consent mechanism built | Omit for v0.1.0 |
| Custom 404 page: content? | GitHub Pages serves its own default 404 | Accept GitHub Pages default for v0.1.0 |
| `vexy-python-markdown-steroids` `.all` shorthand: is it stable? | Need to verify this API exists in the current package version | Fall back to explicit extension list if not |

Any open question not resolved by the time the relevant feature is implemented defaults to the value in the "Default" column. Decisions go in `CHANGELOG.md` when made.
