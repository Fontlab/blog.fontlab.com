# Chapter 10 — Content & Porting Strategy

## Source inventory

Three sources contain potentially portable content:

| Source | Location | Volume | Quality |
|--------|----------|---------|---------|
| WordPress export | `reference/fontlab-com-oldpub/` | ~12 posts, 2013–2023 | Mixed — some gems, much dross |
| FontLab 8 help site | `reference/fldoc/` | Large docs site | Documentation, not blog |
| FontLab VI help | `reference/FontLabVI-help/` | Even larger | Ancient; avoid |

## Retirement policy: what gets dropped

The following content is retired permanently. Do not port, do not archive, do not link to. It is gone.

**Drop all promo and sale posts.** Any post mentioning a discount, a sale, a bundle, a coupon code, or a time-limited offer is retired. These posts have zero residual value and actively undermine the "evergreen" brand of the blog.

**Drop all product point-release notes.** "FontLab 7.2.3 released" posts are retired. Release notes belong in the help site and the app's built-in changelog. A post announcing FontLab 8.3.2 fixed issue #12345 is not a blog post; it was never a blog post; we are retroactively correct about this.

**Drop thin news items.** Posts that are three sentences and a link are retired. If the content was thin in 2018, it is not improved by re-publication in 2026.

## What to port

### From `reference/fontlab-com-oldpub/`

**The 2013 colour fonts article.** This is the crown jewel. A substantive technical piece about colour font formats at a time when the technology was new. It holds up. Port it to Markdown, preserve the original publication date (`date.created: 2013-09-23` or whatever the HTML metadata shows), update any dead external links, and leave the prose alone.

For other posts in oldpub: read each one. If it is a technical explainer that is still accurate, port it. If it is dated, thin, or promotional, retire it. Estimated survivors beyond the colour fonts article: 3–5 posts.

**The `/about/` page.** `reference/fontlab-com-oldpub/about/index.html` contains biographical and company context. Extract and condense into `src_docs/md/about.md`. Target: under 300 words. No direct HTML copy-paste — write it fresh from the source material.

### From `reference/fldoc/`

**News-style content only.** The help site occasionally published "news" posts at the top of major version sections — brief descriptions of new features framed as articles rather than reference documentation. These are candidates. Examples: a piece describing what variable font support in FontLab 8 means for type designers, framed as an explanation rather than a manual entry.

Do not port reference documentation. Do not port step-by-step tutorials that are specific to a UI that may have changed. Do not port anything that reads like a manual chapter.

### From `reference/FontLabVI-help/`

Avoid unless a specific piece is exceptional. The content is older and the UI it describes is several generations removed from the current application. If something truly warrants porting, it must be updated to reflect current reality — at which point it is effectively a new post with historical context, not a port.

## HTML → Markdown conversion

For posts that exist as HTML in oldpub:

1. Use `pandoc` to convert HTML to Markdown as a starting point: `pandoc -f html -t markdown_strict input.html -o output.md`
2. Review the output. Pandoc handles prose well; it handles complex HTML tables and embedded media poorly.
3. Fix code blocks: pandoc often wraps code in indented blocks; convert to fenced blocks with language hint.
4. Strip any WordPress-generated metadata markup (categories, tags div, share buttons).
5. Add front-matter (see [chapter 11](11.md) for the template).
6. Read the result as a human. If it reads awkwardly, fix the prose — do not mechanically preserve every word from 2013 if a sentence can be improved.

## Date preservation

The `date.created` front-matter field controls the post URL and archive placement. For ported content:

- Use the original publication date from the HTML metadata or visible post date
- If only a year is known, use `{year}-01-01` and note the uncertainty in an author comment at the top of the file
- Never use today's date for historical content — it would file a 2013 post under 2026 in the archive

## Link rewrites

Old WordPress posts contain links to:
- `fontlab.com/blog/...` — rewrite to `/blog/...` relative links if the post is ported; drop if the target is retired
- `help.fontlab.com/...` — keep as absolute external links; verify they still resolve
- External third-party links — verify; annotate dead links with a note rather than silently removing them
- Image links — see image handling in [chapter 11](11.md)

## Content freeze

Once ported, content is not continuously updated. The blog is not a wiki. If a technical detail in a 2013 post becomes outdated, the correct response is a new post that references the old one and explains what changed — not a silent edit to the old post. This preserves historical accuracy and gives search engines a clear signal about which post is current.

The sole exception: dead links. Fix dead links in ported content without ceremony.
