# Chapter 5 — Deploy Pipeline

## Trigger

Deploys are tag-triggered. Pushing a tag matching `v*.*.*` to `main` starts the CI workflow. No deploy happens on ordinary commits or pull requests — those run a build-only check without publishing.

This keeps the deploy surface small and intentional. Publishing a post means: merge the PR, then push a tag.

## GitHub Actions workflow

`.github/workflows/ci.yml`:

```yaml
name: CI

on:
  push:
    branches: [main]
    tags: ["v*.*.*"]
  pull_request:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0        # hatch-vcs needs full history for version tags

      - name: Install uv
        uses: astral-sh/setup-uv@v4
        with:
          version: "latest"

      - name: Set up Python
        run: uv python install 3.12

      - name: Install dependencies
        run: uv sync --frozen

      - name: Build site
        run: ./build.sh build

      - name: Sanity check
        run: |
          test -f docs/index.html || (echo "docs/index.html missing" && exit 1)
          test -f docs/CNAME      || (echo "docs/CNAME missing" && exit 1)
          grep -q "blog.fontlab.com" docs/CNAME || (echo "CNAME wrong" && exit 1)

      - name: Deploy to GitHub Pages
        if: startsWith(github.ref, 'refs/tags/v')
        uses: peaceiris/actions-gh-pages@v4
        with:
          github_token: ${{ secrets.GITHUB_TOKEN }}
          publish_dir: ./docs
          publish_branch: gh-pages
          cname: blog.fontlab.com
          force_orphan: true
```

## Branch topology

| Branch | Purpose |
|--------|---------|
| `main` | Source of truth — all authoring and config changes land here |
| `gh-pages` | Published output only — written by CI, never by humans |

`gh-pages` is a force-orphan branch: each deploy replaces the entire branch content. There is no commit history to maintain on `gh-pages` — the build is deterministic from source, so history would be noise.

## CNAME wiring

`docs/CNAME` contains the single line `blog.fontlab.com`. The `peaceiris/actions-gh-pages@v4` action copies this file into the deployed `gh-pages` branch on every deploy. The DNS record at the domain registrar points to GitHub Pages' IP range; GitHub Pages reads the CNAME file to route the custom domain.

The CNAME file must not be deleted by the build. ProperDocs does not touch files already in `docs/` that are not part of the source tree — but to be safe, `docs/CNAME` is also committed to `main` and the CI sanity check verifies its presence and content after every build.

## Rollback procedure

A deploy is just a `gh-pages` branch push. To roll back:

1. Identify the previous good tag: `git tag --sort=-version:refname | head -5`
2. Check out the tag: `git checkout v0.X.Y`
3. Build locally: `./build.sh build`
4. Force-push to `gh-pages`: `git push origin HEAD:gh-pages --force`

This is a manual procedure, intentionally so. Automated rollback logic adds complexity that a low-frequency blog does not need.

Alternatively, re-push an older tag (after deleting the bad one) to re-trigger the CI build from that commit.

## Branch protection

Recommended settings for `main`:
- Require pull request review before merging: yes (at least 1)
- Require status checks to pass (the `build` job): yes
- Restrict pushes: maintainers only

`gh-pages` has no protection rules — it is CI-managed and force-pushed on every deploy.

## Secret management

The workflow uses `GITHUB_TOKEN`, which is automatically provided by GitHub Actions. No additional secrets are required for the initial deploy. If future work adds image optimisation or third-party API calls during build, those secrets go in the repository's Settings → Secrets → Actions, referenced as `${{ secrets.SECRET_NAME }}`.

## First deploy checklist

1. Repository Settings → Pages → Source: `gh-pages` branch, `/ (root)`
2. Add `CNAME` record in DNS: `blog.fontlab.com → fontlab.github.io`
3. Push `v0.1.0` tag to trigger the first deploy
4. Wait for GitHub Pages to provision the TLS certificate (up to 24 hours for first-time custom domains)
5. Verify `https://blog.fontlab.com/` loads correctly
