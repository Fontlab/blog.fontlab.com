# Chapter 11 — Authoring Workflow

## Starting a post

Create a new file in `src_docs/md/blog/posts/`. Name it `YYYY-short-slug.md` where `YYYY` is the intended publication year. The year prefix is purely for editor sorting — it does not affect the URL (that comes from front-matter).

Copy the front-matter template:

```yaml
---
authors:
  - adam
categories:
  - Typography
date:
  created: 2026-05-07
  updated:
draft: true
pin: false
slug:
tags:
  - opentype
  - variable-fonts
---

Write your excerpt here. This is what appears on the blog index page.
Keep it to 2–4 sentences. Make the first sentence count.

<!-- more -->

The rest of the post goes here.
```

Set `draft: true` immediately. This prevents accidental publication of half-finished posts. The draft will be visible in `./build.sh serve` but excluded from production builds.

## Slug rules

- Lowercase, hyphen-separated, no punctuation: `colour-fonts-in-opentype` not `colour_fonts_in_opentype` or `ColourFontsInOpenType`
- Omit dates from the slug (the URL already contains the date from front-matter)
- Keep slugs short: 3–6 words is the target
- Avoid stop words in slugs (`the`, `a`, `in`, `for`) unless they are semantically load-bearing
- If `slug:` is left blank in front-matter, the plugin derives the slug from the filename (minus the year prefix and `.md`). This is acceptable; the explicit field is optional.

## Categories and tags

**Categories** are coarse-grained and strictly controlled. Pick one or two from the allowed list (see [chapter 7](07.md)). If a post genuinely spans three categories, it probably needs to be two posts.

**Tags** are fine-grained and free-form. Use them for specific technologies, tools, or concepts: `COLRv1`, `kerning`, `avar2`, `Python scripting`, `spacing`. There is no enforcement on tag values — but spell them consistently. A tags index that contains both `opentype` and `OpenType` is embarrassing.

## Image handling

Store images in `src_docs/md/blog/posts/img/`. Use descriptive filenames: `colr-table-structure.png` not `screenshot001.png`.

Reference images with a relative path from the post file:

```markdown
![COLR table structure showing layer records](img/colr-table-structure.png)
```

Always include alt text. It is not optional. A post about visual concepts in type design deserves image descriptions that a screen reader can convey.

Image constraints:
- Maximum width: 1200px (MaterialX content area is ~800px; 1200px allows retina rendering)
- Preferred format: PNG for diagrams and screenshots; JPEG for photographs
- Maximum file size: 500KB per image. Compress aggressively — this is a text-heavy technical blog; images should illustrate, not dominate
- No animated GIFs (use a static screenshot with a link to a video if motion is needed)

For images from the oldpub WordPress export: download them from the original CDN URL (if still live) or extract from the WordPress media export. Do not hotlink to the old CDN — those URLs are not guaranteed to persist.

## The `<!-- more -->` separator

Required in every post. The plugin will fail the build if it is absent (`post_excerpt: required`). The excerpt is what appears on the index page, in RSS feeds, and in social card previews.

Write the excerpt as if it is a standalone paragraph — it should make sense without the rest of the post. The reader should be able to decide from the excerpt alone whether the post is worth their time.

## Local preview

```bash
./build.sh serve
```

Opens at `http://localhost:8000`. Live-reloads on file save. Draft posts are visible. This is the only feedback loop needed during writing.

Before committing a post for review:
1. Read the rendered version in the browser, not just the Markdown source
2. Check the excerpt looks correct on the blog index (`http://localhost:8000/blog/`)
3. Check the post appears in the correct category and archive pages
4. Check all images load
5. Check all internal links resolve (the serve command logs 404s to the terminal)

## Draft flag lifecycle

```
draft: true   →   (writing, local review)   →   draft: false   →   PR   →   merge   →   tag   →   live
```

The draft flag is the only publication gate. There is no staging environment. Local serve is the staging environment. When `draft: false` is committed, the post is one tag-push away from being public.

## Link checking discipline

The serve command logs broken internal links. Fix them before removing the draft flag.

External links are not checked at serve time. Before marking a post ready for review, manually verify any external links that are load-bearing (i.e., the post's argument depends on them). See [chapter 12](12.md) for automated link checking in CI.

## Commit conventions

Post commits should be atomic: one commit per post (front-matter + content + images). The commit message format:

```
blog: add post "Title of the Post"
blog: port "Title of Historical Post" from oldpub (original date: YYYY-MM-DD)
blog: fix dead link in "Title"
```

Infrastructure commits (mkdocs.yml changes, CSS tweaks) use a separate commit from content changes. Mixing them makes rollback harder.

## Review and merge

New posts open as pull requests against `main`. The PR template (to be added at `.github/pull_request_template.md`) should include:

- [ ] Front-matter complete and valid
- [ ] `<!-- more -->` separator present
- [ ] `draft: false` set
- [ ] Images compressed and have alt text
- [ ] Internal links verified locally
- [ ] External links verified manually

One approval required. The `build` CI job must pass before merge. After merge, push a version tag to deploy.
