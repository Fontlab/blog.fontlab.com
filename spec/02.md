# Chapter 2 — Architecture

## The stack in one sentence

ProperDocs 1.6.7 converts Markdown source into a static site using the MaterialX 10.1.4 theme, wired together by a thin Fire-based Python CLI and served via GitHub Pages.

## Why ProperDocs, not MkDocs

MkDocs is end-of-life. The upstream maintainer has signalled that MkDocs v2 will carry breaking changes significant enough to invalidate most existing plugin code. ProperDocs is the maintained fork — it tracks bug fixes, ships security patches, and keeps the plugin API stable. The rest of the FontLab toolchain (`fontlab-partners`, the help site) is already migrating to ProperDocs; the blog follows the same path.

The critical compatibility mechanism is a `sys.meta_path` shim shipped by ProperDocs:

```python
# ProperDocs installs this at import time
# Any "import mkdocs.X" resolves to "properdocs.X"
import properdocs  # registers the shim
import mkdocs.config  # works — resolves to properdocs.config
```

This means every third-party MkDocs plugin on PyPI works without a fork or a patch. The plugin ecosystem is enormous; not having to maintain forks of a dozen plugins is a significant operational win.

## Why MaterialX, not MkDocs Material

Same reason: MkDocs Material is the predecessor; MaterialX is the maintained successor from the same lineage. The theme name in `mkdocs.yml` is `materialx`. Visual output is nearly identical. The blog plugin (`materialx/blog`) is the crucial addition — it generates paginated index pages, archive routes, category routes, and author profile pages from post front-matter. No equivalent exists in vanilla MkDocs Material.

## Web Component menu/footer

The MaterialX header is hidden with CSS. Navigation and footer come from a Web Component loaded from `https://i.fontlab.com/menu/fontlab.js`. This keeps the blog visually consistent with the rest of the FontLab web property without duplicating markup or maintaining a custom theme override for every nav change.

The component registers two custom elements: `<fontlab-menu>` and `<fontlab-footer>`. Both live in Shadow DOM, so their styles cannot conflict with page content. Local blog navigation (Home, Archive, About) is passed via a JS config object — no MutationObserver surgery required, unlike the old implementation.

## Python environment

Python 3.12+, managed by `uv`. The CLI package is `blog-fontlab`, installed as a `uv` tool entry point. The `uv.lock` file is committed; CI uses `uv sync --frozen`. Versioning via `hatch-vcs`: the package version is derived from the most recent git semver tag (`v1.2.3`), so no manual version bumps in source files.

## What is deliberately absent

- No Node.js / npm build step. CSS is plain CSS with custom properties. JS is the Web Component, loaded remotely.
- No database. Static site, full stop.
- No CMS UI. Authors write Markdown in their editor and open a pull request.
- No client-side framework. The MaterialX theme ships its own minimal JS; we add nothing on top.
